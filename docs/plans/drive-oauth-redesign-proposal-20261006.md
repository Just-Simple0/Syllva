# Drive OAuth 계획 압축·재설계 제안 (v10 → v11)

상태: 사용자 결정 반영(2026-10-06). v1~v10 원문과 검토 기록은 그대로 보존한다. 제품·테스트·핀 변경 없음.

## 0. 사용자 결정 (2026-10-06)

1. 배포 형태: **개인 전용** (같은 날 후속 결정 "음 복잡하네. 그냥 내 개인 전용으로 scope 줄이자."로 "비개발자에게도 배포"를 대체). 사용자 본인의 Cloud 프로젝트에 Desktop OAuth client 하나를 만들고 본인만 쓴다. Google 심사·보안 평가·배포 준비 기록과 최대 경과 판정 gate를 계획에서 뺀다. 준비 상태는 "설정에 client 값이 있다"로 판단한다. Homebrew/npm 배포와 공용 client는 범위 밖이다. 이 범위는 프로젝트 정의(개인용 학습 지식·검색 시스템)와 맞아 동결 명세 개정이 필요 없다.
2. R2·R3 저장 단계 단순화: **채택.** 1회용 승인 객체·공용 재사용 차단 기록·committing poll을 없애고 commit 요청 안에서 저장하고 결과를 응답한다.

후속 결정 "오픈소스로 공개하는 방향으로 하고, 내가 비개발자 대상으로 운영하는 건 이후 확장하는 단계로 보자":

- 지금 단계: 오픈소스 공개를 전제로 한 개인 사용. 저장소와 패키지에는 OAuth client 값을 넣지 않고, 사용자마다 자기 Cloud 프로젝트의 Desktop client를 설정한다. 설정 방법은 문서로 안내한다.
- 확장 단계(이번 범위 밖): 운영자가 공용 client를 두고 비개발자에게 제공. 그때 Google 검증·보안 평가·배포 준비 상태 표시를 별도 계획으로 다룬다. P2는 이 확장을 막지 않도록 client 값을 설정 bundle에서만 읽고 코드에 고정하지 않는다.
- 공개 자체(저장소 공개 전환, 라이선스 선택, 개인 식별값·설정 정리)는 별도 작업이며 사람 결정 뒤에 한다.
3. R4 네트워크 상한 단순화: **채택.** 하위 프로세스·호출 수 상한 대신 표준 클라이언트의 연결·읽기 타임아웃, redirect·재시도 0, 응답 크기 상한을 쓴다.
4. **P1(Drive 개인정보 보강)을 먼저** 별도 계획·검토·구현한다. OAuth 계정 식별값 결속은 P2로 옮긴다.

v10 A-1(Pro) 결과 REVISE2/OPTIONAL1은 승인 객체 재검증과 consume 순서 문제로, R2 채택으로 해당 구조가 사라지므로 v11에서 대체된다.

## 1. v10이 결정한 내용 (요약)

- **목적과 권한:** 검색(MCP)은 `drive.readonly`, 자료 처리(WORKER)는 `drive`. 두 목적은 OAuth client와 Cloud project를 따로 쓴다. School 폴더 지정은 Syllva 내부 대상 제한이며 Google 권한을 좁히지 않는다. `drive.file`/Picker는 제외.
- **연결 흐름:** 설정 화면 "Google 계정 연결" → 시스템 브라우저 로그인·동의 → 로컬 callback에서 code 교환과 계정 확인 → 화면이 CSRF 보호 POST로 저장(commit) → 저장 결과를 다시 읽어 확인한 뒤 성공 표시. 기존 서비스 계정 JSON은 고급 경로로 유지.
- **저장:** 기존 CredentialService 트랜잭션(잠금 순서·journal·복구)을 그대로 쓰고, OAuth 전용 저장 함수와 엄격한 authorized_user 6-key 파서를 추가한다.
- **보안 경계:** state/PKCE, loopback·정확한 host/path, cross-site callback용 좁은 쿠키 예외, 고정 오류 코드, 토큰·client secret 비노출.
- **운영 경계:** 앱 미준비 시 OAUTH_APP_NOT_READY, School ACL·owner_only 유지, 개발용 서비스 계정 접근권은 OAuth 완료 뒤 별도 인간 승인으로 정리.
- **Drive/intake 보강:** driveId 형식 오류 거절, 파생 파일 생성 후·게시 전 재검증, 재사용 파생 파일 공유 상태 확인, 처리 전 폴더 권한 재확인, WORKER 계정 식별값 결속.

## 2. 왜 커졌나

1. **덮어쓰기 누적:** v5부터 매 판이 "앞 판 원문 전체 + 맨 위 보완 절" 구조라, 같은 주제가 여러 판의 규범으로 겹쳐 있고 우선순위 설명이 따로 필요해졌다. v10 952줄 중 상당 부분이 승계 원문과 이력이다.
2. **범위 혼합:** OAuth와 무관한 기존 Drive/intake 결함 보강(D/D2)이 같은 문서에 들어와, 검토마다 Drive·intake 소스 전체가 따라붙었다.
3. **설계 자체의 경계면 증가:** A(흐름)와 B(저장)를 분리하면서 "1회용 승인 객체 + 프로세스 공용 재사용 차단 기록 + TTL·용량·tombstone"이 생겼고, 저장을 비동기 poll로 관찰하게 해 "300초 뒤에도 저장 중", "다른 탭에서 진행 중" 같은 경계 상태가 계속 나왔다.
4. **배포 전제가 불분명:** 비개발자 일반 배포를 전제로 Google 심사 증거 기록과 not-ready gate까지 설계했지만, 실제로 누구에게 배포하는지는 정해지지 않았다.

## 3. 재설계안

### R1. 작업을 셋으로 나눈다

| 묶음 | 내용 | 의존 |
|---|---|---|
| P1 Drive 개인정보 보강 | driveId 파서, DerivedDriveWriter·_stage_derivative 재검증, 처리 전 폴더 권한 재확인, 공개 진입점 식별 확인 | OAuth와 무관, 지금 결함이므로 먼저 구현 가능 |
| P2 OAuth 연결 핵심 | 설정값, 흐름 상태, callback, 저장, 런타임 갱신, 연결 테스트 | P1과 독립 |
| P3 설정 화면 | 카드·버튼·문구·focus, fake-browser 회귀 | P2의 응답 형식 |

각 계획은 30KB 안쪽, 단일 규범 문서로 쓴다. 이력·지적 추적표는 별도 파일로 뺀다.

### R2. 1회용 승인 객체와 공용 차단 기록을 없앤다 (권장)

commit POST가 flow 객체의 잠금 안에서 `awaiting_commit → committing`을 한 번만 바꾸고, 같은 요청 안에서 B의 `save_google_oauth(candidate)`를 직접 호출한다. B의 이 함수는 외부 route에 노출하지 않고 flow만 호출한다. 재사용 방지는 flow 상태 하나로 끝나고, 별도 승인 객체·TTL 256칸 기록·프로세스 epoch 키가 필요 없다. 재시작 복구는 지금처럼 journal이 맡는다.

### R3. 저장 결과를 commit 응답으로 바로 돌려준다 (권장)

commit 요청은 저장이 끝날 때까지 기다렸다가 고정 결과 코드를 응답한다(상한 시간 안). 화면은 그 응답 뒤 자격증명·Overview를 다시 읽고 성공을 표시한다. "300초 뒤에도 저장 중" 상태와 committing poll이 사라진다. 응답을 잃으면 "결과 미확인 + 다시 확인" 안내만 하고 자동 재시도하지 않는다.

### R4. 네트워크 상한을 단순화한다 (선택)

현재: 모든 OAuth 통신을 별도 하위 프로세스에서 실행하고 경로별 호출 수(2/14/10/8)와 30초 상한, 1MiB 상한을 둔다. 대안: 같은 프로세스에서 표준 HTTP 클라이언트에 연결·읽기 타임아웃, redirect·재시도 0, 응답 크기 상한만 둔다. DNS 무응답처럼 타임아웃이 안 걸리는 드문 경우는 화면에서 취소 후 재시도로 처리한다. 코드와 테스트가 크게 줄지만 "어떤 경우에도 정해진 시간 안에 끝난다"는 보장은 약해진다.

### R5. 배포 형태를 먼저 정한다 (결정 필요)

Google 공식 문서 기준, 외부(External) 앱이 "테스트" 상태이면 Drive 권한 갱신 토큰은 동의 후 7일 만에 만료된다. 7일 제한을 없애려면 앱을 "프로덕션"으로 바꿔야 하고, Drive 권한은 민감/제한 범위라 Google 심사와 경우에 따라 보안 평가가 필요할 수 있다.

- **본인 전용(권장 출발점):** 사용자 본인의 Cloud 프로젝트에 Desktop client를 만들고 본인만 쓴다. 준비 상태는 "설정값이 있다"로 충분하고, 심사 증거 기록·만료 판정 gate를 뺀다. 7일 만료를 피하는 방법(프로덕션 전환 시 미검증 앱 경고 표시 등)은 실제 동작을 확인해 안내한다.
- **다른 비개발자에게 배포:** Google 심사·보안 평가가 실제 전제이며 코드만으로 끝나지 않는다. 이 경우에만 지금의 배포 준비 gate를 유지한다.

### R6. 검토 방식을 바꾼다

- 계획 검토는 "계약 결정"까지만 받는다. 경계 상태의 세부 동작은 테스트 표에 넣고 구현 FINAL에서 실제 코드로 검토한다.
- 계획 + 관련 소스를 중복 없이 3~5개 묶음으로 나눈다.
- P1은 작은 버그 수정 범위라 계획 1회, FINAL 1회로 끝낼 수 있다.

## 4. v11 문서 구성 (각 계획 공통)

1. 목표와 고정 결정 (1쪽)
2. 불변식 목록 (I1, I2 … 한 줄씩)
3. 구성요소별 계약: 상태·입출력·실패 시 효과

5. 수락 테스트 표 (시나리오 → 기대 효과 수)
6. 남는 사람 작업 (앱 등록, 로그인·동의, ACL 정리, 실제 School 흐름)

## 5. 사용자 결정이 필요한 것

1. 배포 형태: 본인 전용 / 다른 비개발자 배포 (R5)
2. R2·R3 단순화 채택 여부 (권장: 채택)
3. R4 네트워크 상한 단순화 여부
4. P1을 OAuth보다 먼저 별도 작업으로 구현할지 (권장: 먼저)
