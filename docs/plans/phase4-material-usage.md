## 3. Strict ranges and graph

Missing/null on BOTH bounds means whole source. Finite bounds must be positive integral numbers with start <= end. A supplied invalid bound is never converted to missing. Reject bool, zero/negative, fractional, non-finite and malformed string values; integer-valued JSON floats may be explicitly normalized at the Notion adapter boundary. One-sided bounds are unsupported/incomplete and excluded with a warning, never widened. PAGE_RANGE must explicitly supply both keys, including null/null for a human-reviewed whole-source expansion.

Validate every requested finite page against the current derivative's actual page index, not just Page Count. Missing/duplicate/contradictory markers cannot establish page evidence. Remove the fallback that labels an unmarked whole body with an arbitrary requested page range; surface SOURCE_PARTIAL/UNAVAILABLE when no justified locator exists. Explicitly change `retrieval/freshness.py:revalidate_locator` to use the SAME validated page-index/marker logic as page_chunks. No valid indexed marker for a matched symbolic term means None, never fabricated p1; _session_signals discards that unresolved stale locator. Cover no markers, duplicates/contradictions/gaps across both paths so stale revalidation cannot restore a page that ordinary validation rejected.

A usable Usage needs a nonempty ID/Role and exactly one Session and Material. Its Session must equal the requested session; both entities must exist and resolve, through §10's exact Course lookup, to the same Course relation page (and therefore the same Course Key). Never take the first of multiple relations. Invalid rows are excluded with warnings and receive no capability. The same validator runs before initial reads and follow-up authorization.

Role cannot promote source_class/ownership; §9 defines the exact, separate derivation. Preserve existing valid roles by mapping them explicitly. No placeholder ellipsis.

## 5. Discovery and explicit operations

Query `get_material_usage(session_id)`; do not assume one row per Session/Material or per Session/Material/Role. Same-role disjoint or partially-overlapping ranges coexist as independent Usage relations — overlap alone is never ambiguous and never merged; only an **exact** duplicate (same Session, Material, Role, start, end) is ambiguous.

Candidates explicitly choose `create_usage` or `update_range`:

- `create_usage` searches all valid rows by exact Session/Material/Role/range. Reuse an exact matching user's actual ID. An existing unverified row still needs a MATERIAL_USAGE approval proposal; an identical verified row is a no-op. Different ranges — including partial overlaps of an existing row — do not overwrite existing rows: they create distinct usage proposals.
- `update_range` requires a real `usage_id`, validates its Session/Material, and binds old Role/range/Verified plus the exact desired range. Do not infer the first row from a material or role. Missing/ambiguous target gives AMBIGUOUS/review-needed without writes.
- Multiple exact duplicate rows are ambiguous, not an invitation to choose one, create another, merge or delete.

**Sibling duplicate check (closes review blocker 2, creation half).** Immediately before persisting a `create_usage` write (both the Usage row and its Queue proposal) and immediately before applying an approved `update_range`/PAGE_RANGE patch (§8), re-query `get_material_usage(session_id)` for the target Session/Material pair and recompute the exact-duplicate set. If the write's resulting (Role, start, end) would exactly duplicate another row's current (Role, start, end) under a **different** `usage_id`:
- for `create_usage` at persistence time: do not create a second Usage row; treat as the existing-unverified/no-op case above against the sibling instead;
- for an approved `update_range`/PAGE_RANGE application: do not patch; mark the proposal `SUPERSEDED` with reason "would create a duplicate sibling Material Usage", per §8's "changed source/target becomes SUPERSEDED" rule.

A new Usage ID is `MU:` plus a digest of canonical JSON `[session_id, material_id, exact_role, start, end]`. This is an app-level relationship ID, not a source allocation or locator entity ID. Discovery cannot rely solely on regenerating that ID. No lossy role slug or delimiter-collision identity.

## 6. Immutable proposal identity and schema

Store typed canonical JSON in the existing Proposed Action Rich text, not invented Notion properties. It includes schema/operation, exact Usage target/logical DB, Session/Material ID and the resolved Course relation page ID plus Course Key (§10), old target snapshot (relations, Role, bounds, Verified), trusted Material Type and resolved source class, exact desired patch, BOTH Session and Material canonical source refs/hash/versions, grounded evidence/explicit absence, Review Reason/explicit absence, and processor version. This exact set is the **canonical approval semantics**.

`domain/approval_identity.py` defines two pure functions used by both the producer and the applier — never duplicated logic:

```text
canonical_semantics_from_queue(record) -> OrderedMapping
derive_proposal_id(proposal_type, semantics) -> str
```

`canonical_semantics_from_queue` extracts the fields listed above from the Queue record's own Proposed Action JSON. Full Session/Material/Course binding semantics exist inside that JSON. The real optional Queue Course relation is a checked mirror, not a replacement for the full Course identity. Before deriving identity, validate every present schema-defined mirror (Proposal Type, Target Entity ID, Course, Source Ref, Source Hash/Version, Evidence and Review Reason) against its corresponding action value; reject conflicting aliases, duplicate JSON keys, unknown semantic fields and mismatched mirrors. Target DB and Target Fingerprint are NOT §14.7 Queue properties: logical target DB and target snapshot exist only inside canonical Proposed Action JSON. Derive/validate logical DB against Proposal Type and configured database identity. Legacy Python convenience fields must be removed from persisted property maps, not added to the Notion schema. A present Course mirror must contain exactly the action's single relation page ID. Compare Source Ref using only canonical provider + file_id; navigational web_url is excluded from identity and semantic hashing. A web_url-only change cannot change the Proposal ID or fail source-identity equality. Optional Source Ref/Hash/Version mirrors all refer to the SAME Material dependency; both dependencies remain explicit in the action. Required semantic JSON keys must be present, including null values; omitted keys cannot be normalized into explicit null. No caller-supplied candidate is authoritative. `derive_proposal_id` is `type namespace + digest(canonical JSON of semantics)`. MATERIAL_USAGE therefore binds initial page bounds and Session fingerprint too. Identical semantics retry under one ID; changed action, role, range, dependency hash OR version, target, Course binding or evidence produces another. Display-only Name/Confidence are excluded from semantics and may change freely. Review Reason is bound human-review context, not mutable display metadata. Optional absent mirrors do not invent action values; present conflicting mirrors fail closed.

For EVERY Queue state, retries compare all immutable fields and deny mismatches BEFORE writing. Explicit null is a value, not an omitted field. Normalize allowed aliases/JSON string vs mapping without accepting conflicting aliases. Apply this at both upsert and guarded adapter write boundaries. Terminal REJECTED/SUPERSEDED/FAILED cannot be revived automatically. Same rejected semantics stay rejected; a genuinely new semantic proposal gets a new ID. Manual resubmission generations are not implemented here. APPLIED replay performs no duplicate mutation.

Usage creation uses only §14.4 fields, including required Name/ID/Session/Material/Role and Verified=false; no Source Hash/Version on Usage. Queue creation supplies Name, Proposal ID/Type, State=PENDING_REVIEW, Decision=Pending, Proposed Action and defined optional properties. Created/Updated are provider-owned. §14.3 Materials also has no Source Hash: authoritative hashes come from the trusted Drive/state SourceFingerprint capability, not invented graph fields. Courses (§14.1) have no `ID` property at all — only `Name`, `Aliases`, `Course Key`, `Code`, `Section`, `Semester`, `Professor`, `Status` — so Course identity in stored semantics is always `{relation_page_id, course_key}`, never a fabricated Course `ID`.

Revalidate dependencies → create missing unverified Usage → create Queue. Queue failure retries the same Usage/Proposal identity; discovering the created row must not skip its pending verification proposal. Never overwrite an existing row's scope to match a new candidate before approval. Report orphan unverified creation/retry state; confirmed retrieval excludes it.

## 7. Guarded write boundary

**Physical Queue uniqueness.** The guarded backend adds `find_approval_rows(proposal_id: str) -> Sequence[QueueRow]`, preserving all physical matching rows and their provider record IDs (separate from logical Proposal ID). Complete filtered pagination is required, or scanning until a second match establishes ambiguity; a truncated one-row page cannot prove uniqueness. The public singular `read_approval` delegates to one shared 0/exactly-1/>1 validator: no row is missing, one row is authoritative, more than one is an integrity error. Never deduplicate by Proposal ID or choose the first, even with identical semantics.

Use this SAME unique lookup for upsert, ApprovalReader, HumanApprovalApplier, immediate pre-write checks and recovery. Mutations target the uniquely resolved physical record internally; callers never choose arbitrary provider row IDs. Strict Fake stores Queue rows by physical ID and can seed external duplicate Proposal IDs with differing State/Decision. >1 permits no target or Queue mutation, no merge/delete and no success claim. Source binding and Queue uniqueness backends are required for the guarded path; no silent fallback to legacy singular reads that cannot establish the invariant.

After Queue create, including create-committed-then-raised, reread unique matches before retry: exactly one identical proposal is reused; zero remains retryable; >1 is ambiguity. Recheck trusted dependencies and canonical semantics before reuse. Do not create another row merely because a create response was lost. This does not claim CAS against concurrent external insertion; the single-worker visibility limit remains.

A concrete provider-neutral guarded wrapper maps configured database UUIDs to logical DB names and checks every create/update/region-write path. Unknown DBs and malformed schema/cardinality fail closed. Its strict Fake backend executes the same guards; retrieval gets a separate narrow reader.

Keep all existing human-only protections. Ordinary AUTOMATION cannot mutate existing Usage Session/Material/Role/bounds/Verified; harmless metadata may use an explicit allowlist. It cannot change Queue approval semantics via direct updates, aliases, or AI-region writes. Stateful immutable checks belong in the wrapper, composed with the existing pure policy guard. Ordinary AUTOMATION cannot set Decision By, Decision At or Applied At, on creation, updates, aliases or region writes. Decision creation is only Pending. Only the internal applier writes attribution/application timestamps after a valid current approval; ApprovalReader only derives allowed State transitions from the human Decision. Internal failure transitions are narrowly state/error writes and do not grant audit-field authority. Apply the same restrictions to upsert; strip or reject caller audit inputs rather than forwarding them as harmless metadata. Approval capabilities (`APPROVAL_READER`, `HUMAN_APPROVAL_APPLIER`) are internal, not caller-selected free-form actor strings, per frozen §15.2.1. Applier constructs only the exact patch for the approved operation; no general MCP write/approval tool.

The writer supplies authoritative Queue read by Proposal ID and guarded mutations; it need not expose graph-reader methods. ApprovalSourceReader uses the existing read-only DriveReader method names from `src/uls/adapters/drive/base.py`: `read_derived(source_ref: SourceRef) -> str` and `get_current_fingerprint(source_ref: SourceRef) -> SourceFingerprint`. A narrow wrapper may adapt existing broader signatures. Each call receives the bound canonical SourceRef, not a graph hash or caller-chosen file; service failures remain structured/retryable. Producer, retrieval and applier may share a reader implementation but never collapse it into general write authority. Test separate writer and reader objects, with the writer deliberately lacking Course lookup.

Application sequence:

1. Re-read trusted Queue. A caller-supplied mismatch is denied without terminalizing the legitimate stored proposal.
2. **Self-validate the stored row before trusting it (closes review blocker 1).** Compute `semantics = canonical_semantics_from_queue(current)` and `expected_id = derive_proposal_id(proposal_type, semantics)`. If `expected_id != current`'s own stored `Proposal ID` property, the row is treated as malformed authoritative state: return a structured identity-integrity error with zero target AND zero Queue mutations, and stop. Do not repair identity or alter a possibly tampered record under the old approval. This runs on the **stored** row itself, independent of any caller-supplied argument, so a direct Notion edit to `Proposed Action`, `Target Entity ID`, Session/Material/Course binding, role/range, either source ref/hash/version, or evidence — while leaving the `Proposal ID` string unchanged — is caught even when the applier is invoked by Proposal ID alone. Only after this passes does the frozen §15.2.1 precondition list apply: State==APPROVED, Decision==Approve, target exists, not already terminal, source fingerprint valid where applicable, action structurally valid.
3. Read current Usage, Session, Material and Course; compare exact old graph/scope snapshot. Validate both source dependencies through one explicit injected trusted source-reader Protocol; no Usage/Materials hash fallback or model `based_on`. Re-run §5's sibling-duplicate check for both MATERIAL_USAGE verification and `update_range`/PAGE_RANGE before patching; another exact sibling created since approval prevents either mutation.
4. Revalidate current page index and desired action. MATERIAL_USAGE sets only Verified=true after verifying its approved full relation/range snapshot. PAGE_RANGE changes only explicitly approved bounds and preserves Verified.
5. Recheck Queue semantic ID/mirrors, target, sibling duplicates, Course/Type/Role policy and BOTH dependencies immediately before one target property patch, read back its result, then write audit metadata and Queue APPLIED last.

**Decision By is not an application precondition (closes review blocker 5).** Frozen §15.2.1 lists valid Proposal ID, State==APPROVED, Decision==Approve, target existence, non-terminal state, source-fingerprint validity, and structural validity as the complete precondition set; a pre-existing stored `Decision By` is not among them, and §15.2.1 explicitly states the applier *records* `Decision By`, `Decision At`, `Applied At` as an output of application, not an input gate. `HumanApprovalApplier.apply()` must not require the stored Queue row to already carry a valid human `Decision By` before proceeding. At write time, the recorded `Decision By` is resolved in this order: (a) the stored row's existing `Decision By` if it already passes the human-value check (`_is_human_decision_by`) — preserved as-is; else (b) the applier's own constructor-level trusted reviewer identity (the existing `decision_by: str | None` constructor argument), which must independently pass `_is_human_decision_by` and is supplied by the applier's deployment/invocation context, never by a caller-request field; else (c) if neither (a) nor (b) yields a valid human value, the applier fails closed with `PolicyViolation("no attributable human decision_by is available")` and performs no mutation — an application can proceed without a *pre-existing* `Decision By`, but it can never record an automation/blank one. Ordinary AUTOMATION remains unable to write `Decision`, `State∈{APPROVED,REJECTED,APPLIED}`, or select this capability, per §15.1/§54.

An identity/mirror/parse failure that prevents establishing a valid semantic identity causes zero mutations. An identity-valid but structurally invalid action may become FAILED; changed source/target/sibling-duplicate becomes SUPERSEDED; caller forgery merely denies with no legitimate-row mutation. Temporary trusted-service unavailability returns a retryable no-write error, not a claim that the source changed. Map errors to frozen §53 taxonomy. Do not accidentally treat an out-of-range current page count as a generic caller error by ordering checks incorrectly.

A target-write exception is an **unknown outcome**, not proof of failure. Do not immediately mark Queue FAILED. Read back through the trusted graph reader, recheck semantic identity and BOTH source/graph dependencies, then:
- Exact approved desired result: finish the same audit-recovery path without another target write.
- Exact old snapshot with retryable provider failure: retain APPROVED and return retryable, with no terminal/success claim; subsequent retry revalidates everything before writing.
- Divergent result, or unavailable/inconclusive read-back: retain a recoverable Queue state and return a structured reconciliation-required error. Do not overwrite a later human edit or claim success. Recovery repeats exact-state/identity/dependency checks; no unconditional second write.

Tests require a Fake that mutates then raises, raises before mutation, and mutates then makes read-back unavailable. Prove eventual single-mutation APPLIED in the first case, safe retry in the second, and recoverable/no-success/no-human-overwrite in the third.

A provider success return is also insufficient by itself: unavailable/divergent immediate read-back follows the same recoverable reconciliation path and must not write APPLIED. Test normal return plus unavailable/divergent read-back.

If target patch succeeds but Queue audit fails, return APPROVED/audit-pending. Replay may finish audit without another target write only if the target equals the exact approved desired result and identity plus all source dependencies (and §8.2's self-validation) still match. Any mismatch is not evidence of successful application. Preserve subsequent human edits. Failed read-back/recovery yields a structured safety error, never success.

Use the single-active-worker model. Do not claim provider/cross-store CAS that does not exist. External human edits between final read and write remain a documented visibility window, mitigated by immediate rechecks/read-back and explicit failure/reconciliation. Live validation remains pending until a real provider satisfies the documented path. No fake proof of zero race window.

## 9. Source authority: Usage Role vs Material Type vs source_class (closes review blocker 3)

Frozen §14.3 gives Materials a required `Type` (Select) and frozen §14.4 gives Material Usage a required `Role` (Select); frozen implementation and design text nowhere enumerates either Select's option set or a Role→authority mapping — this is genuinely deployment-configured, not a frozen enum, confirmed by grep across both frozen documents. Rev4 does not invent frozen values; it defines the missing derivation contract explicitly, grounded in the existing `retrieval/authority.py:SOURCE_CLASS_TO_AUTHORITY` registry (already-shipped code, not new invented values):

- `usage_role` (Material Usage.Role) and `source_class`/`SourceAuthority` are separate axes. Phase 4 deployment Role values are exactly `Primary`, `Supporting`, and `Reference`, compared as exact strings. All three make a valid Usage eligible for the existing intent policy; none adds an allowed source class or elevates authority. Missing/unknown values are excluded with a warning and no capability. These are deployment defaults, not frozen enums. Schema-invalid old fixtures missing Role/Type must be migrated explicitly; no compatibility fallback guesses a role. Intent policy AND role eligibility AND verification/config rules must all pass.
- `source_class` is derived **only** from the Material's own trusted `Type` property, read from the Notion graph record already fetched by the engine (`get_material`/`_material_for_usage`), never from Usage Role and never from derivative front matter (§16's `uls.material.v1` front matter has no `Type` field).
- Add a new `retrieval.material_type_source_class: dict[str, str]` config entry (loader/validation/example, alongside the existing `retrieval:` block in `config.example.yaml`). Each value must be exactly `professor_material` or `supplemental_reference`, the two supported Material source classes. Other registry classes (e.g. official_activity, user_source, ai_enrichment) are not valid Material authority mappings and fail config validation at load time (fail closed before any request is served).
- Ship one safe example deployment default (documented as configurable, not frozen):

  ```yaml
  retrieval:
    material_type_source_class:
      "Lecture Slides": professor_material
      "Professor Notes": professor_material
      "Syllabus": professor_material
      "Textbook": supplemental_reference
      "Reference": supplemental_reference
      "Supplementary": supplemental_reference
  ```

- An unmapped or missing Material `Type` at request time is a fail-closed condition: exclude that Material's evidence from the assembled context (`SOURCE_UNAVAILABLE` warning, "material type is not mapped to a source authority"), and deny capability issuance for it. It must never default to `professor_material`, `supplemental_reference`, or any other class.
- Fix BOTH direct `get_material_context` and Session retrieval to look up `source_class` via this mapping keyed by the Material's `Type` (fail closed as above) instead of the current hardcoded `source_class="professor_material"`.

## 10. Course identity and relation lookup (closes review blocker 4)

Frozen design §9 defines Course Key as `{semester}_{course_code}-{section}` (e.g. `2026-1_COMP319-002`); frozen §14.1 gives Courses `Name`/`Aliases`/`Course Key`/`Code`/`Section`/`Semester`/`Professor`/`Status` and explicitly no `ID` property; §14.2/§14.3 give Sessions and Materials a `Course` relation ("Relation → Courses, exactly 1"). The current `NotionReader` protocol (`base.py:174-210`) has no exact Course-by-relation lookup — only `get_course_by_alias`, which is a fuzzy/alias entry point, not an exact graph dereference — and the generic `record_id` compat helper (`_compat.py:114-120`) reads `ID`/`Entity ID`/`id`/`entity_id`, none of which exist on Courses, so it cannot resolve Course identity either.

Rev4 adds exactly one new read-only method to `NotionReader`:

```python
def get_course_by_relation_id(self, relation_page_id: str) -> Any | None:
    """Exact dereference of one Course by its provider relation page ID."""
```

and `domain/course_identity.py`:

```python
def resolve_course_relation(relation_value: Any) -> str | None:
    """Extract the single relation page ID from a Course relation field, or None."""

def course_key_of(course_record: Any) -> str | None:
    """Read the Course's own Course Key (Rich text) property, or None."""
```

Validation contract, applied wherever the plan requires "the current Course":

1. Read the entity's `Course` relation; it must resolve to exactly one relation page ID via `resolve_course_relation`. Zero or multiple relations is invalid (excluded with a warning; no capability).
2. Fetch the Course record via `get_course_by_relation_id`; a missing/deleted Course is invalid.
3. Read `course_key_of(course_record)`; a blank/missing Course Key is invalid. Use the existing parse_course_key grammar and validate Code/Section/Semester components against the fetched Course record; matching arbitrary nonblank strings does not establish a valid academic identity.
4. Where a normalized derivative is also in play (Session transcript, Material derivative), its own `front_matter.course_key` (§16) must equal the Course Key fetched in step 3. A mismatch is a drift condition, not a fallback to either value — treat identically to a stale/invalid dependency (§4/§8).
5. "Session and Material share the current Course" means their two relation page IDs (step 1) resolve to the same Course page. Require both page-ID and exact Course Key equality in the fetched snapshots, with immediate rechecks to catch in-place edits. No fuzzy or alias fallback.

Store `{relation_page_id, course_key}` — never a fabricated Course `ID` — in canonical approval semantics (§6) and in separate `CapabilityBinding.course_relation_page_id` and `course_key` fields (§9) for later revalidation. Capability revocation (§11) must detect a Course relation rewire even when the Course Key string happens to stay the same (page ID changed) and a Course Key edit on the same page (page ID unchanged, key text changed).

Required acceptance tests: zero/multiple Course relations on Session or Material; relation to a deleted/missing Course; Session and Material linked to two different Course pages that happen to have similar/identical `Name`; matching relation page ID with mismatching derivative `front_matter.course_key`; Course relation rewired to a different page after capability issuance (must deny at follow-up); Course Key text edited in place on the same page after capability issuance (must deny at follow-up, per freshness rules already required by §11); the valid one-relation/matching-Course-Key case succeeds.
