# 학습 UX 정의 독립 리뷰 요청

작성일: 2026-09-13. 대상: `docs/ux/file-intake.md`의 2026-09-12 정의안.
현재 작업은 설계 리뷰이며 제품 구현·외부 Notion/Drive 변경은 포함하지 않는다.

## 사용자가 정한 방향

- 학기별 Notion 페이지가 대시보드 역할을 하고 과목 접근, 과제·학사 일정, 해야 할 일을 담는다.
- 기본 접근 순서는 대시보드 → 과목 → 세션이다.
- Drive 학기 폴더의 `+` 업로드함 하나에 자료를 넣고 시스템이 디렉토리를 정리하면 좋겠다.
  그것이 어렵다면 미리 정의한 과목별 폴더에 사용자가 넣는 방식도 수용한다.
- 강의자료·전사문·교과서·실습 문제·내 풀이를 어떻게 넣는지 이해하기 쉬워야 한다.
- 실제 알고리즘 1 테스트에서 짧은 요약은 학습용으로 부족했다. 설명·예제·증명/계산·
  연습문제·해설·근거까지 담긴 결과물이 필요하다.
- 실제 수업 날짜는 2026-03-06, 전사는 `1주차.md`, 강의자료는
  `Lec2-Algorithmic Analysis I.pdf`다. 자료 번호와 세션 번호는 같다고 볼 수 없다.

## 리뷰 질문

이 정의안이 위 학습 경험을 충족하는 일관된 제품 설계인지, 다음 구현에 들어가기 전에
반드시 결정하거나 수정해야 할 실제 결함은 무엇인지 판단해 달라.

검토 범위는 입력·분류·파일 이동·수업 연결·학습·대시보드·확인/실패/알림 동선과
frozen 모델/권한 경계 및 현재 구현과의 정합성이다. 첨부 소스는 현재 구현 사실을 확인하는
근거다. 전체 저장소 코드의 무관한 버그 감사나 아직 미구현이라는 이유만으로 결함을
만드는 리뷰는 하지 말라. 설계가 '후속 설계'로 유보한 항목 중에서도 첫 사용 경로를 막는
것과 구현 시 정할 수 있는 세부사항을 구분하라.

외부 서비스의 최신 UI/API 기능을 확인하지 않았다면 구현 가능하다고 단정하지 말고,
문서 내부에서 선택이 누락된 것인지 실제 서비스 제약인지 구분해 표시하라.
정의안에 있는 텍스트 화면 예시만 제공된다. 동작하는 UI·모바일 화면을 검증했다고 주장하지 말라.

## 응답 형식

1. 한국어로 결론: GO 또는 REVISE와 구체적인 이유. 제품 방향의 적합성과 구현 착수 준비도를 구분.
2. 차단 결함/중요 결함을 우선순위대로 최대 6개. 판정마다 파일/라인/문구 또는 코드조각을 인용하라.
   발생 상황 → 사용자에게 생기는 문제 → 최소 수정안 → 확인 가능한 수용 사례를 적어라.
3. 별도의 선택적 개선은 최대 3개. 선호나 미래 확장을 필수 결함과 섞지 말라.
4. 유지할 설계와, 사용자 결정이 꼭 필요한 항목만 제시하라.
5. 가장 작은 실제 사용 가능한 첫 구현 범위를 제안하되 제품 방향을 임의로 바꾸지 말라.

현재 정의안과 첨부만 근거로 독립 평가하고, 같은 프로젝트의 과거 채팅이나 다른 리뷰의
결론을 답습하지 말라. 파일을 수정하거나 새로운 작업을 위임하지 말라.
