# 학습 대시보드·파일 입력 UX 리뷰

작성일: 2026-09-13. 대상: [UX 정의안](file-intake.md), 2026-09-12 스냅샷.

## 결론

**제품 방향은 적합하며, 구현에 들어가기 전 정의 보완이 필요하다(REVISE).**
웹 ChatGPT와 독립 Gemini 검토가 같은 큰 결론을 냈고, 아래 여섯 항목은 현재 assistant가
명세·코드를 대조해 범위와 우선순위를 정리한 최종 판단이다. 제품 코드를 구현하거나 정의안을
개정한 결과가 아니다. 미구현 자체를 결함으로 세지 않고, 첫 사용 경로에서 결정이 빠져 있거나
현재 계약에 그대로 연결하면 의미가 달라지는 부분을 다룬다.

리뷰 경로:

- 사용자 요청 `insane-review` 엔진의 구독 ChatGPT 웹 리뷰. 실제 검증된 표시는
  **GPT-5.6 Sol (매우 높음)**이다. Pro 비활성 상태를 확인했고 사용자가 사용량 제한과
  대체 진행을 명시했다. Pro 리뷰로 표기하지 않는다.
- 별도 맥락의 `gemini-review-high`: **google-antigravity/gemini-3.8-flash / high**.
  초기 보고서의 인용·스키마·서비스 단정 오류를 교정 요청하고 수정 보고서까지 검토했다.
- UI 증거는 정의안의 텍스트 화면 예시다. 실제 Notion 버튼·모바일·Drive 이동 API는 검증하지 않았다.

## 구현 전 필수 보완

### 1. [P1] ‘범위 미확인’과 ‘자료 전체 사용’을 구분해야 한다

정의안 §5의 사용 범위 예시(253–269행)는 `미확인`을 허용한다. 하지만
`src/uls/domain/page_range.py:121`은 시작·종료 페이지가 모두 비어 있으면
`WHOLE_SOURCE`로 해석한다. 로컬 재현에서도 `parse_page_range(None, None)`이
`whole_source`를 반환했다.

**발생 상황:** 사용자는 PDF가 해당 수업 자료라는 사실만 알고 페이지는 모른다. 구현자가
빈 페이지를 그대로 승인 대상에 매핑하면 ‘범위를 모른다’가 ‘전체를 사용했다’로 확대될 수 있다.
현재 운영 시연에서 잘못 승인됐다는 뜻은 아니며, 다음 UI 연결에서 막아야 할 의미 차이다.

**최소 보완:** 사용자에게 `미확인 / 지정 페이지 / 전체 자료`를 분명히 구분해 제시한다.
‘전체 자료’는 명시적 선택으로만 승인 대상에 넣는다. 미확인 후보와 검증된 사용 관계를 분리하고,
정확한 대상·버전·범위에 대한 사람 확인을 기존 HumanApprovalApplier 경계에 연결한다.

**수용 사례:** 과목·자료 관계만 확인하고 페이지를 비워도 전체 자료 승인으로 바뀌지 않는다.
별도로 ‘전체 자료 사용’을 선택한 경우에만 전체 범위 제안을 확인할 수 있다.

### 2. [P1] ‘기존 수업 선택’이 실제로 그 수업에 연결되는 경로가 필요하다

정의안 §4.2(185–195행)는 `새 수업 / 기존 수업 선택`을 제공한다. 반면
`src/uls/worker.py:169`는 원본별 Session ID를 할당하고,
`src/uls/ingestion/transcript_ingest.py:328`의 `_bind_source_entity()`는 호출자가 준 ID를
할당 결과와 비교할 뿐 기존 수업을 선택하는 명령으로 취급하지 않는다. 불일치 시 오류를 낸다.

**발생 상황:** 대시보드에 3월 6일 수업을 먼저 만들어 두고 전사를 나중에 올린다.
화면에서 기존 수업을 골라도 현재 경로를 그대로 쓰면 새 수업을 할당하거나 연결이 실패할 수 있다.

**최소 보완:** ‘새 수업 생성’과 ‘기존 수업에 전사 연결’을 별도 동작으로 정의하고,
정확히 선택된 과목·수업에 연결하는 worker 경로, 재시도, 원본과 수업의 기존 연결 충돌을 정한다.
현재 source-bound allocation 계약과 달라지는 부분은 frozen 명세 대조·필요 시 개정 대상으로 둔다.

**수용 사례:** 기존 3월 6일 수업을 선택해 전사를 넣으면 새 Session ID가 생기지 않으며,
재처리 후에도 같은 수업 하나에 연결된다. 같은 날짜의 다른 수업과도 합쳐지지 않는다.

**판단:** 웹 리뷰가 제안한 ‘첫 버전에서 기존 수업 선택 제거’는 범위를 줄이는 대안일 뿐이다.
대시보드에서 수업을 먼저 관리하는 사용을 고려하면, 이 기능을 유지하고 연결 계약을 정하는 쪽을 권한다.

### 3. [P1] 과목·날짜 미정 파일의 대기 기록과 확인 화면을 정해야 한다

정의안 §2.2(92–108행)는 과목 미정 파일을 정식 Session/Material로 만들지 않는다고 한다.
이 원칙은 타당하다. 다만 현재 등록 경로는 유효한 Course를 요구하고
frozen 구현 명세 §8의 `source_files.course_key`도 필수다. 따라서 별도 접수 계층의
저장·조회·수정·승격 규칙이 있어야 대시보드의 ‘확인할 파일’이 동작한다.

**발생 상황:** 파일을 넣고 과목이나 강의 날짜를 아직 고르지 않은 상태에서 PC가 재시작된다.
대기 기록과 원래 위치를 보존하지 않으면 사용자는 파일을 다시 올리거나 같은 질문에 다시 답해야 한다.

**최소 보완:** 정식 수집 전 접수 기록을 지속적으로 보관하고, 파일 identity·원래 위치·현재 버전·
선택한 학기/과목·누락 정보·이동/실패/승격 상태를 추적한다. Notion에는 그 기록을 확인하는
구체적인 화면을 정한다. 과목·날짜를 입력하면 어느 기록이 바뀌고 언제 다음 단계로 넘어가는지 명시한다.
학술 개체를 임시 보관소로 쓰거나 가짜 과목을 넣지 않는다.

**수용 사례:** 과목 미정 파일 접수 → PC 재시작 → 같은 확인 항목 유지 → 과목·날짜 입력 →
정확히 한 번 정식 등록. 이동 중 실패해도 원본 위치와 재시도 상태를 찾을 수 있다.

**판단:** Gemini의 ‘모든 접수 정보를 Automation Queue에 넣기’는 그대로 채택하지 않는다.
`OTHER`라는 enum이 있다는 사실만으로 새로운 입력·실행 계약이 생기지 않는다.
과목·날짜 입력을 별도 승인으로 만들 필요도 없다. 기존 승인 큐를 재사용한다면 필드 소유권,
payload 형식, 처리기와 권한을 먼저 검증해야 한다.

### 4. [P1] ‘학습 노트 만들기’의 실행·저장·갱신 경로를 정의해야 한다

정의안 §6(299–328행)는 ‘학습 노트 만들기’와 `준비됨 / 원본 변경으로 갱신 필요` 상태를
약속하지만, 사용자 요청을 누가 받아 생성하고 어디에 쓰는지 구체화하지 않았다.
MCP 검색은 읽기 전용이므로 이 버튼을 검색 MCP의 쓰기 기능으로 구현할 수는 없다.

**발생 상황:** 사용자가 노트 생성을 요청하거나, 이미 노트를 만든 뒤 강의자료가 개정된다.
실행 경로와 근거 버전이 없으면 클릭이 처리됐는지 알 수 없고 오래된 노트를 최신으로 볼 수 있다.

**최소 보완:** `사용자 생성 요청 → 사용할 근거 확정 → 허용된 별도 생성·쓰기 경로 →
Notion AI 영역 반영 → 사용한 원본/범위/버전 기록`의 흐름을 고정한다.
요청 접수·생성 중·실패·준비 상태를 표시하고, 근거가 바뀌면 갱신 필요로 표시한다.
USER 필기와 복습 상태는 보존한다. 구체적인 Notion 블록 디자인은 이후에 정해도 된다.

`[날짜 입력]`, `[사용 범위 확인]`, `[학습 노트 만들기]`가 각각 어떤 화면 조작인지도
정의해야 한다. 속성 편집, 확인 화면, 링크, 버튼 중 실제 구현할 방식을 정하고 실행 결과를 보여준다.
이번 리뷰는 Notion 버튼이나 웹훅이 불가능하다는 서비스 판정이 아니다.

**수용 사례:** 전사 v1로 노트 생성 → 준비됨 → 전사 v2 등록 → 기존 노트는 갱신 필요 →
재생성 후 v2에 연결. PC가 꺼져 있다면 생성 완료 대신 대기와 최근 확인 시각을 보여준다.

## 중요 보완

### 5. [P2] 개인 할 일·학기 공통 일정의 기준 저장소를 정해야 한다

정의안 §2.1(54–68행)은 이들을 대시보드 핵심으로 두면서 저장 방식을 유보한다.
Activities/Exams는 과목에 속하는 학술 개체이므로, ‘수강 변경 마감’ 같은 공통 일정을
억지로 넣으면 의미가 달라진다. 대시보드와 과목에서 같은 과제가 중복 기록되는 것도 피해야 한다.

**최소 보완:** 개인 할 일·학사 일정은 사용자/대시보드 기록임을 명시하고 기존 Notion DB를
재사용할지 별도 저장소를 둘지 결정한다. 과목 과제·시험은 기존 학술 기록을 연결해 표시한다.
완료 상태와 일정 수정의 주체도 정한다.

**수용 사례:** 학기 공통 일정은 과목을 요구하지 않고 대시보드에 보인다. 같은 과목 과제는
대시보드와 과목 페이지에서 동일한 마감·완료 상태를 보여준다.

**판단:** 웹 리뷰의 ‘첫 버전에서 개인 할 일·공통 일정 제외’는 가장 작은 기술 시연 범위로는
가능하지만 사용자 대시보드 요구를 완성한 버전은 아니다. 자동 추출은 미뤄도 기존 기록 표시나
수동 입력을 포함해 요구한 화면을 충족하는 편을 권한다.

### 6. [P2] 전사 판별과 낮은 확신도의 유형 확인을 맞춰야 한다

정의안 §4.2(174–183행)는 `.md/.txt`와 `[0:01]` 같은 두 부분 시간 표시를 허용한다.
그러나 `src/uls/ingestion/classifier.py:62`는 내용에서 세 부분 시간 표시만 판별한다.
로컬 합성 입력 확인 결과:

| 파일 이름과 본문 | 현재 분류 결과 |
| --- | --- |
| `1주차.md`, `[0:01]`·`[15:35]`만 존재 | material, confidence 0.5 |
| `1주차.md`, `[1:05:13]`도 존재 | transcript, confidence 0.8 |

**최소 보완:** 분류기와 전사 정규화기의 지원 시간 형식을 맞추고, 약한 기본 분류를 정식 자료
유형으로 자동 확정하지 않는다. 불명확하면 자료 종류를 확인하는 접수 상태로 보낸다.

**수용 사례:** 두 부분 시간 표시만 있는 전사가 전사 후보 또는 유형 확인 대상으로 접수되며,
자동으로 Material이 되지 않는다.

**판단의 한계:** 실제 시연 파일 전체가 오분류됐다는 주장은 채택하지 않는다. 기존 시연은
transcript 유형을 명시했고, 실제 원문에는 세 부분 시간 표시도 있었다. 확인된 문제는
두 부분 시간 표시만 있는 파일 또는 그런 부분만 분류 입력으로 제공하는 경우의 호환성이다.
현재 native worker가 이 분류기를 통해 오분류했다는 재현은 아니다.

## 채택하지 않은 주장과 선택적 개선

- **기본 업로드 방식 재질문:** 불필요하다. 단일 업로드함 기본·과목 폴더 선택이라는 사용자
  방향을 유지한다. 과목 폴더부터 구현하는 순서는 내부 검증용으로 선택할 수 있지만,
  그것만으로 단일 업로드함 요구를 완료했다고 하지 않는다.
- **폴더 이름 변경·이동이 SourceRef를 즉시 파괴한다는 초기 주장:** 기각했다.
  identity는 `provider + file_id`다. 정리 결과가 사용자에게 찾기 쉬운지와 이동 전후 권한·링크·
  재시도는 별도로 확인해야 한다. 표시용 한글 트리와 실제 보관 경로는 하나의 구체적인 예로 맞춘다.
- **임의 Queue enum/필드·Session.Status 작업 상태 추가:** 기각했다. frozen에 없는 값은
  그대로 사용할 수 없고, USER 학습 상태를 시스템 작업 상태로 재사용하지 않는다.
- **교과서 전체에 단일 페이지 오프셋 적용:** 기각했다. 검증된 구간에서만 사용할 수 있으며,
  이는 기존 정의안 §4.3의 원칙을 유지하는 것이다.
- **선택적 UI 개선:** 노트 상단에 `전사만 / 확인된 PDF 포함 / 임시 자료 포함` 근거 범위를
  보여주고, 대시보드에 최근 동기화 시각을 표시한다. ‘같은 과목 지정’과 ‘같은 세션 지정’은
  별도 일괄 조작으로 둔다.
- **알림:** 외부 알림 선호를 지금 다시 물을 필요는 없다. 첫 정의에서는 대시보드 배지와
  확인 항목을 명시하고, 휴대폰/메일 알림은 별도 요구가 생길 때 범위를 정한다.

운영 연결 전에 실제 학교 과목 코드·분반은 확인해야 한다. 이는 리뷰를 막는 질문이 아니며,
이번 리뷰 때문에 기존 테스트 Course ID를 변경하지 않았다.

## 다음 설계 보완의 범위

화면 구성을 전면 재설계할 필요는 없다. 다음 문서 개정에서는 네 가지 연결을 구체화하면 된다.

1. 업로드 접수 기록 ↔ Notion 과목·날짜 입력 ↔ 정식 등록·원본 정리.
2. 전사 원본 ↔ 새 수업 생성 또는 정확한 기존 수업 연결.
3. 자료 사용 후보 ↔ 미확인/지정 범위/전체 구분 ↔ 사람 확인과 적용 결과.
4. 노트 생성 요청 ↔ 허용된 AI 쓰기 경로 ↔ 근거 버전·갱신 상태.
